// OVERVIEW

A UI speedometer built for my racing game during the year one 3D Level Design module of my Bachelor's. It was my first proper piece of work with Unity's UI system, and I designed the dial elements myself in Photoshop. The speedometer reads its target vehicle's velocity in real time and displays it through both an analogue needle and a digital centre readout, with a game version adding dash warning lights for braking and slipping.

// DEV LOG

The core of the system is a controller that reads the velocity from the target car's rigidbody, converts it to a chosen unit (MPH or KPH), and drives the display from there. The needle rotates by mapping the current speed to an angle between a set minimum and maximum, clamping at the top end so it never overshoots past the dial.

The speed labels around the dial are generated procedurally based on the target car's top speed, so the markings always match whatever vehicle the speedometer is attached to rather than being hard-coded. Each label is spaced evenly around the dial by the same normalised angle calculation that drives the needle. I also added a digital centre display showing the live speed and unit, using an image mask so the needle reads cleanly over the top of it.

I later wrote up the whole build as a step-by-step tutorial and published it on GitHub, covering the UI setup, the controller script, and the procedural labels.

// CHALLENGES & LEARNINGS

As my first time working with Unity's UI system, a lot of the learning came from understanding how the canvas actually renders — UI elements draw in hierarchy order, so my procedurally spawned labels initially appeared on top of the needle. Setting the needle as the last sibling after generating the labels fixed it, and it gave me an early, practical grasp of how Unity's UI layering, Rect Transforms and pivots fit together — knowledge I've relied on in every project since.

// OVERVIEW

A technical research project for the Machine Learning module (COMP714) of my AI for Games Master's at Falmouth University. The aim was to investigate whether a reinforcement learning (RL) agent could learn to play a boxing game in real time against a finite state machine (FSM) driven opponent. I built it in Unreal Engine 5 using the Learning Agents plugin, training an agent to perceive game state — location, stamina, enemy position, health and targeting — and learn effective combat behaviour from it.

// DEV LOG

The agent was built in UE5's Blueprints with control over movement, look direction, attack and lock-on (I removed jumping early on, as it served no purpose in boxing and only complicated the action space). The core of the project was reward shaping, carried out across three experiments, each trained for 2+ hours with episodes fixed at 500 steps.

Run one used a generous reward setup and produced an agent that punched almost constantly, burned through stamina, and rarely scored — yet still returned high rewards, a clear sign they weren't reflecting good behaviour. Run two tightened the structure and added signals for staying in range and conserving stamina, giving slightly smarter play but still inflated returns. Run three stripped back the passive rewards so the agent had to earn its return through genuine combat rather than simply surviving.

// RESULTS

Run three produced a clear improvement, with the agent consistently landing one to two kills per episode by the end of training. Peak average returns reflected the tuning — roughly 640 and 710 in the first two runs against a lower but harder-won ~250 in the third, where negative returns drove continued learning. The agent never reliably beat the FSM bot and kept some bad habits (occasional air-punching, wasted stamina), but the experiments clearly showed that reward shaping directly and predictably influenced both behaviour and training stability.

// CHALLENGES & LEARNINGS

Most of the friction came from Unreal's runtime quirks: Blueprints losing references after editor restarts (fixed by manually reconnecting nodes), the FSM NPC occasionally failing its state transitions, and the player spawning at the world origin and being destroyed in inference mode (fixed with an explicit default spawn location). The biggest takeaway was how sensitive RL is to the reward function — minor changes produced large, sometimes counter-intuitive shifts, and getting returns to actually reflect performance was as much of the challenge as the combat itself. The project met its goal of applying ML in a real gameplay scenario, and demonstrated both the potential and the practical limits of reinforcement learning in UE5.
